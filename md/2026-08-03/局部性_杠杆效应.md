“为调用方提供杠杆效应”就是：**调用方只付出很少的代码和认知成本，就能获得模块内部大量、稳定、正确的行为。**

可以把它理解成：

> 少量输入 → 获得大量能力。

## 没有杠杆效应

假设业务要“注册用户”，调用方自己处理所有细节：

```ts
async function registerController(req: Request) {
  const email = req.body.email.trim().toLowerCase();

  const existingUser = await db.user.findUnique({
    where: { email },
  });

  if (existingUser) {
    throw new Error("邮箱已存在");
  }

  const passwordHash = await bcrypt.hash(req.body.password, 12);

  const user = await db.user.create({
    data: {
      email,
      passwordHash,
      status: "active",
    },
  });

  await emailService.sendWelcomeEmail(user.email);
  await auditLog.record("user.registered", user.id);

  return {
    id: user.id,
    email: user.email,
  };
}
```

这里调用方需要知道：

- 邮箱要标准化
- 如何检查重复
- 密码哈希参数
- 用户默认状态
- 欢迎邮件
- 审计日志
- 返回值过滤

调用方承担了几乎全部复杂度，**杠杆效应很低**。

---

## 有杠杆效应

把这些行为放进一个深模块：

```ts
const user = await userRegistration.register({
  email: req.body.email,
  password: req.body.password,
});
```

模块接口很小：

```ts
interface UserRegistration {
  register(input: { email: string; password: string }): Promise<RegisteredUser>;
}
```

但内部完成：

```ts
class UserRegistrationService {
  async register(input: RegisterInput): Promise<RegisteredUser> {
    const email = normalizeEmail(input.email);

    await this.ensureEmailAvailable(email);

    const passwordHash = await this.passwordHasher.hash(input.password);

    const user = await this.userRepository.create({
      email,
      passwordHash,
      status: "active",
    });

    await this.welcomeEmail.send(user.email);
    await this.auditLog.record("user.registered", user.id);

    return {
      id: user.id,
      email: user.email,
    };
  }
}
```

现在调用方只需要知道一件事：

```ts
userRegistration.register(...)
```

但获得了七八项正确行为。这就是杠杆。

## 为什么叫“杠杆”

现实中的杠杆是：

> 用较小的力，撬动较大的重量。

代码中的杠杆是：

> 用较小的接口，调用较大的行为集合。

可以粗略写成：

```text
调用方杠杆 = 模块提供的有效行为 / 调用方需要理解的接口复杂度
```

例如：

```text
register(email, password)
```

接口只有两个参数，却封装了：

```text
校验 + 去重 + 哈希 + 持久化 + 发邮件 + 审计 + 返回值保护
```

杠杆很高。

反过来，如果模块只是：

```ts
function getUser(id: string) {
  return db.user.findUnique({ where: { id } });
}
```

它只是给数据库调用换了个名字，调用方获得的额外能力很少，杠杆效应就弱。

## 判断一个模块有没有给调用方提供杠杆

看调用方代码是否从：

```ts
做 A
做 B
判断 C
处理 D
调用 E
补偿 F
```

缩减为：

```ts
module.doThing();
```

而且模块不是简单转发，而是真正承担了业务规则、错误处理、一致性和基础设施细节。

所以 `code-base design` 追求的不是“把代码包一层”，而是：

> **找到一个干净的接口，让调用方不必理解内部复杂度，就能安全地完成一整件事。**

---

“为维护者带来局部性”就是：**修改一个功能时，维护者只需要关注一个有限区域，而不必在整个代码库里到处追踪规则。**

这里的“局部性”不是单纯指代码写在同一个文件，而是：

> 与某个业务行为相关的规则、状态和错误处理，集中在一个清晰的模块边界内。

## 没有局部性

还是以“用户注册”为例。

注册逻辑散落在不同调用方：

```ts
// web controller
const email = req.body.email.trim().toLowerCase();
await db.user.create(...);
```

```ts
// admin controller
const email = req.body.email.toLowerCase();
await db.user.create(...);
await sendWelcomeEmail(email);
```

```ts
// import script
await db.user.create({
  data: {
    email: row.email,
    status: "active",
  },
});
```

现在增加一条规则：

> 新用户注册时，必须记录审计日志。

维护者必须全局搜索：

```text
user.create
createUser
insert user
register
importUser
```

然后判断：

- 哪些地方属于注册
- 哪些地方要加审计
- 哪些地方不能加
- 有没有遗漏的调用方
- 每个调用方实现得是否一致

这种代码的复杂度是**分散的**，没有局部性。

---

## 有局部性

所有注册行为都通过一个模块：

```ts
await userRegistration.register({
  email,
  password,
});
```

注册规则集中在这里：

```ts
class UserRegistrationService {
  async register(input: RegisterInput) {
    const email = normalizeEmail(input.email);

    await this.ensureEmailAvailable(email);

    const passwordHash = await this.passwordHasher.hash(input.password);

    const user = await this.userRepository.create({
      email,
      passwordHash,
      status: "active",
    });

    await this.auditLog.record("user.registered", user.id);
    await this.welcomeEmail.send(user.email);

    return user;
  }
}
```

现在增加审计日志，维护者只需要修改和测试：

```text
UserRegistrationService
```

不需要了解所有 Controller、脚本和入口。

这就是局部性：

```text
业务变化
   ↓
定位到一个模块
   ↓
在模块内部修改
   ↓
通过模块接口测试
```

## 局部性主要解决三个问题

### 1. 理解是局部的

维护者想知道“用户是怎么注册的”，直接看：

```ts
userRegistration.register();
```

而不是在代码库里拼图。

### 2. 修改是局部的

修改注册规则时，主要改注册模块，不需要同步修改十个调用方。

### 3. 验证是局部的

可以直接通过公开接口测试：

```ts
it("注册成功后记录审计日志", async () => {
  await registration.register({
    email: "test@example.com",
    password: "12345678",
  });

  expect(auditLog.record).toHaveBeenCalledWith(
    "user.registered",
    expect.any(String),
  );
});
```

不需要分别测试 Web、后台管理、CLI、定时任务里的重复逻辑。

## “调用方杠杆”和“维护者局部性”的关系

它们是同一个模块从两个角度产生的价值。

对于调用方：

```ts
registration.register(input);
```

少量代码获得完整注册能力，这是**杠杆效应**。

对于维护者：

```text
注册规则主要集中在 registration 模块
```

修改时只需要关注这个区域，这是**局部性**。

可以总结成：

```text
小接口 → 调用方获得杠杆
高内聚实现 → 维护者获得局部性
清晰边界 → 所有人获得可测试性
```

需要注意，局部性不等于“所有代码塞进一个大文件”。真正的局部性是：**维护者可以从一个模块入口出发，在模块内部完成理解和修改，不需要跨越大量不相关的系统边界。**
